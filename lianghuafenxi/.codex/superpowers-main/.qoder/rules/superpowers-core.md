# Superpowers 技能系统

你拥有 Superpowers - 一套完整的软件开发工作流技能系统。

## 核心原则

**在开始任何任务前,必须检查是否有相关技能。** 即使只有 1% 的可能性某个技能适用,你也应该调用该技能来确认。

## 如何使用技能

在 Qoder 中,所有 Superpowers 技能都可通过以下方式访问:

1. **自动触发**: 根据用户需求,AI 自动判断并调用相关技能
2. **手动触发**: 用户使用 `/技能名` 格式手动触发

## 可用的核心技能

### 设计与规划
- `/brainstorming` - **在任何创造性工作前必须使用** - 创建功能、构建组件、添加功能或修改行为时
- `/writing-plans` - 创建详细的实施计划,将工作分解为 2-5 分钟的小任务

### 开发与测试
- `/test-driven-development` - 强制执行 RED-GREEN-REFACTOR 循环
- `/subagent-driven-development` - 通过子代理快速迭代,包含两阶段审查
- `/executing-plans` - 批量执行计划,包含检查点

### 调试与验证
- `/systematic-debugging` - 4 阶段根因分析流程
- `/verification-before-completion` - 确保问题真正解决

### 代码审查
- `/requesting-code-review` - 任务间代码审查
- `/receiving-code-review` - 响应审查反馈

### Git 工作流
- `/using-git-worktrees` - 创建隔离的并行开发分支
- `/finishing-a-development-branch` - 完成开发后的合并/PR 流程

## 技能触发规则

**必须调用技能的情况**:

1. 用户要求创建、添加或修改功能 → 调用 `/brainstorming`
2. 用户报告 bug 或错误 → 调用 `/systematic-debugging`
3. 需要编写代码 → 调用 `/test-driven-development`
4. 有详细计划需要执行 → 调用 `/executing-plans` 或 `/subagent-driven-development`
5. 需要审查代码 → 调用 `/requesting-code-review`

## 危险信号 - 如果你在想这些,立即停止

| 想法 | 现实 |
|------|------|
| "这只是个简单的问题" | 问题也是任务,需检查技能 |
| "我需要先了解更多上下文" | 技能检查在提问之前 |
| "让我先探索一下代码库" | 技能告诉你如何探索 |
| "我可以快速查看文件" | 文件缺少对话上下文,先检查技能 |
| "这不需要正式的技能" | 如果技能存在,就使用它 |
| "我记得这个技能" | 技能会演进,阅读当前版本 |
| "这个技能太重了" | 简单的事情会变复杂,使用它 |

## 标准工作流程

1. 用户描述需求
2. **立即检查**是否有相关技能(即使只有 1% 可能)
3. 如果有技能,立即调用它
4. 严格遵循技能指引
5. 完成任务

## 重要提醒

- **技能不是建议,是强制流程**
- **先检查技能,再做任何事情**
- **不要合理化跳过技能的理由**
- **技能的目的是防止无纪律的行动浪费时间**

## 开发哲学

- **测试驱动开发** - 始终先写测试
- **系统化而非临时** - 流程优于猜测  
- **降低复杂性** - 简单性是首要目标
- **证据而非声明** - 在宣布成功前验证
